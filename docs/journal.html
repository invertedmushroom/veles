Veles — The Journal: Durability & Recovery

Every fact the system will ever need again is an appended record in a content-addressed journal, owned by the Worker kernel and persisted in IndexedDB. Reload is not a reset; it is a resume, because the truth was written down before anything happened.

Append-only, typed, complete

The journal's record vocabulary covers a run's whole life: RunCreated, RunPreparing, CheckpointCommitted, ApprovalRequested, ToolDenied, ToolIntentLogged, ToolDispatched, ToolResultCommitted, RunInterrupted, RunCompleted, RunCancelled, RunFailed. Run states, interrupt reasons (user_reload_or_tab_close, gateway_disconnected_safe_to_retry, uncertain_tool_outcome), and gateway operation stages are all closed unions in the protocol — not string conventions.

Intent before effect

The core ordering invariant (KERN-INV-01): commit the tool intent before its effect, and stage result blobs before publishing their hashes in the journal transaction. In code, the dispatch path appends ToolIntentLogged, then ToolDispatched, and only then invokes the executing adapter; the result is committed last. A crash anywhere in that sequence leaves a visible, interpretable trail — an intent that never dispatched, or a dispatch that never committed — never a silent half-effect.

Content-addressed blobs, staged writes

File content lives in a ContentAddressedBlobStore over OPFS: bytes are hashed with sha256, identical content deduplicates, and reads verify the hash — a missing blob is a hard ERR_BLOB_MISSING error, not truncated output. Writes stage to a temporary name and are published to the canonical hash only after staging succeeds, so a failed write cannot leave a partial blob behind a valid address. The journal's file tree maps paths to those hashes; context building surfaces each committed file with an 8-hex prefix and annotates folded prior runs when a file's hash has since drifted.

One writer per workspace

Multi-tab safety comes from Web Locks: the first tab's Worker takes the workspace lease as ReadWrite_Leader; other tabs become ReadOnly_Observer. Observer mode is enforced at the store level — writes and mutations throw ERR_READ_ONLY_OBSERVER — and switching or deleting a workspace releases the previous lease and acquires the target workspace's lease via LockProvider. A deterministic in-memory provider mirrors the same protocol for unit tests.

Recovery: reload is a resume

On boot the Worker acquires the lease and reads the journal tail. A run left mid-flight is resolved by an explicit recovery decision: for dispatched-but-uncommitted gateway operations, the kernel queries the gateway's status endpoint and, when the outcome is found, commits it (COMMITTED_BY_BROWSER); otherwise the run becomes RunInterrupted with a named reason. The conservative rule (KERN-INV-02) is that a dispatched non-idempotent effect whose gateway vanished becomes interrupted: uncertain_tool_outcome — it is never silently replayed. Retrying an interrupted run is an explicit user act, permitted with a recorded reason.

Archives and optimistic UI

Workspaces export and import as archive bundles; restoring an older archive discards newer files and journal rows rather than layering them. The UI renders optimistically — a submitted prompt appears immediately as an ephemeral message — but only RunCreated and later commits make it durable, and journal events stream to the UI only after the underlying commit succeeds. A quota failure mid-commit notifies no subscribers, and subscriber errors or explicit detach() calls never affect durable writes.
