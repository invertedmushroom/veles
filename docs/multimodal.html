Veles — How Images Reach the Model

Multimodality in Veles is model-facing. User chat prompts are text-only — there are no image parts on RunCreated turns — only tool results that carry an imageDataUrls field, which the next inference round staples back onto the conversation as image parts.

The mental model

Images can enter the workspace via the Files browser upload, web.fetch_url, or image generation tools, but they only enter the model's vision context when the model calls an image tool. The model decides to look, a tool loads or produces the pixels, and the harness attaches them on the following round.

The image tools

  • workspace.inspect_image — loads an image from the browser workspace into multimodal vision context. This is how the agent sees anything, including its own generated results.
  • image.generate / image.transform — produce or edit an image; the committed result carries the image data URL for the next round.
  • web.fetch_url — emits no images itself, but pulls remote bytes into the workspace so inspect_image can load them.

A typical chain: fetch a URL (possibly retrying, since HTML pages are not image bytes), inspect the file, then transform it — each step a decision the main agent made and the journal recorded.

Wire serialization

When a message carries imageDataUrls, each URL becomes one content part, by kind:

URL kindWire form
Raster data URL (png / jpeg / webp / gif base64)Vision part {type: "image_url"} — base64 embedded in the JSON request body.
http(s):// URLVision part — sent as a link for the API to fetch.
SVG data URL (image/svg+xml, utf8 or base64)Decoded and inlined as a text part, [Attached SVG Image Markup] — the model reads SVG as markup, no vision needed.
Anything else — including an SVG disguised as image/png (base64 payload starting PHN2Zy)Silently dropped.

Context economics

Images do not live in context forever. Attachment is gated on the hot-run window — only recent runs re-carry their images (default: the last two runs); older tool results keep their text (longer outputs are folded) and drop their images. Even for attached images, context accounting budgets each at min(length, 4000) characters against the round's character budget, so a long run never accumulates megabytes of base64 per round.

The generation cascade

image.generate and image.transform hand the actual pixels to a provider cascade inside the tool handler — a sequence of model calls the main agent initiated but does not supervise:

  1. Remote disabled by configuration? Done before any network: a local deterministic provider renders hash-seeded gradient SVG artwork from the prompt. Offline runs still produce committed files.
  2. Transforms start with a vision side-call. The source image and the edit instruction go to the chat-vision model, which writes a vivid text-to-image prompt preserving subject, pose, and composition while applying the edit. If that side-call fails, the original instruction is used unchanged — the transform still proceeds.
  3. Raster endpoints, in order. An edit via the Responses API's image_generation tool (source image inlined as input_image), then dall-e-3, then gpt-image-1 via /images/generations, then a plain Responses generation. Text-to-image endpoints cannot receive the source image at all — for those, the image crosses by proxy, as the side-call's prose.
  4. Chat-model SVG fallback. The chat model authors raw <svg> XML — raster sources attached as an image part, SVG sources inlined as markup.
  5. Local deterministic SVG. The same offline provider as step 1, as the last resort.

Provenance rides along: the prompt is tagged [source:<workspace path>], and the committed result text names the path that won — for example [Generated raster PNG via openai:responses.image_generation]. The main agent sees the one-line result and the named route, and can inspect_image the output to check it.
