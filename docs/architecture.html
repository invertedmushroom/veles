Veles — Architecture Walkthrough

A browser-native agent runtime: the browser tab is the whole computer. A Web Worker owns every durable fact; everything remote is disposable.

The one rule

A single Web Worker owns workspace files, conversations, approvals, and the run journal, persisted in IndexedDB and OPFS. The UI renders typed projections it receives over a MessagePort bridge and never writes state directly. Remote inference and tool execution are ephemeral: useful while running, never the authority for committed state. If the network, a provider, or the gateway disappears mid-run, the journal still tells the truth after reload.

Who owns what

Life of a tool call

  1. Intent committed. The kernel writes the tool intent to the journal before anything executes — a crash here leaves a visible, recoverable record, not a mystery.
  2. Dispatch committed. The call is marked dispatched, then the adapter executes it: a browser tool in-Worker, or an HTTP/SSE call to the ephemeral gateway.
  3. Result staged, then committed. Output lands in the content-addressed blob store first; only afterwards does the journal commit the result. Readers never observe half-written state.

Crash recovery

On boot the Worker acquires the workspace lease, reads the journal tail, and reconciles anything that was in flight: it queries the gateway's status endpoint for dispatched-but-uncommitted operations, or interrupts them with a known reason. Because every transition was journaled before it happened, reload is a resume, not a reset.

Isolation boundaries

  • Preview sandbox: generated apps render in an opaque-origin iframe; they can never reach the kernel's storage or the parent origin.
  • Capability-scoped gateway: each gateway boot has a fresh identity, a bearer check, capability scopes, bounded subprocess execution in temp directories, and a hard operation TTL.
  • Provider independence: inference is an OpenAI-compatible SSE adapter; providers are configuration, not architecture.
