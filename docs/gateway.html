Veles — The Ephemeral Execution Gateway

When an agent's tool needs a real filesystem or subprocess — things a browser cannot grant — the call crosses to a small Node server built to be disposable. The gateway owns zero durable state (SEC-INV-02): kill it at any moment and the journal on the browser side still tells the truth.

Ephemeral by construction

Each boot generates a fresh identity — gw-<uuid> — and nothing else: no workspace store, no conversation store, no database. The browser-side client pins the instance identity it negotiated with and rejects responses from any other, so a restarted gateway is a different service, not a confused continuation of the old one. Operations the gateway remembers exist only to answer "did that finish?" — they carry an expiry, are reaped when it passes, and the hard ceiling on any operation is five minutes (300,000 ms), enforced regardless of what the client asked for.

Every request passes four independent gates

  1. Authentication. When a token is configured, only the exact Bearer match is accepted; tokenless operation exists for local development.
  2. Protocol validation. Commands are validated against the versioned protocol before anything executes.
  3. Capability scope. The requested tool must appear both in the request's allowedTools scope and in the gateway's own registered set (sandbox.exec, sandbox.WriteFile, inference.stream by default). Scopes can constrain writable paths and network access; the network allowlist is probed once per boot and the result cached.
  4. Resource limits. A per-operation timeout aborts the subprocess (ERR_GATEWAY_TIMEOUT), cancellation propagates (ERR_GATEWAY_OPERATION_CANCELLED), and output size is bounded.

Subprocesses in disposable sandboxes

Executed tools run inside a fresh temporary directory (veles-gw-sandbox-*) that is unconditionally deleted in a finally block — on success, on error, on timeout, on expiry. In restricted mode (the default), node subprocesses run under Node's permission model (--permission with scoped --allow-fs-read / --allow-fs-write and conditional --allow-net) and reject host-loading startup flags (ERR_GATEWAY_RUNTIME_FLAG_DENIED). Escape attempts fail loudly with ERR_GATEWAY_SANDBOX_ESCAPE. Output is redacted against secret patterns (sk-, gsk_, apikey_, ghp_, bearer strings become <REDACTED>) before it is returned, and the returned outcome carries the output's sha256 alongside any file updates it produced.

Operations have stages, and recovery uses them

Each operation advances through ACCEPTED → STARTED → COMPLETED, streaming events as it goes. The status endpoint reports the stage, outcome, and error code for any unexpired operation — exactly what the kernel's recovery path queries after a reload finds a dispatched-but-uncommitted tool call. If the gateway (or its memory of the operation) is gone, the run is interrupted as uncertain_tool_outcome rather than guessed. Cancellation is an explicit abort-and-delete.

Running it

The gateway lives at services/gateway/server.ts, speaks plain HTTP, and needs no database or configuration beyond an optional bearer token. Its client adapter on the browser side is GatewayToolExecutionAdapter in src/kernel/gateway-client.ts; serving only the built dist/ without the gateway produces explicit tool errors — the system degrades by naming what is missing, never by silently weakening isolation.

Verify it yourself

npm test   # offline, no credentials

tests/gateway.test.ts asserts authentication, scope enforcement, TTL expiry and reaping, sandbox lifecycle, output redaction, stage transitions, and the status endpoint the recovery flow depends on; tests/kernel-runtime.test.ts covers the browser-side reconciliation decisions.
