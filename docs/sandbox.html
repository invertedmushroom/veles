Veles — The Isolated Preview Sandbox

Agent-generated apps render inside the workbench, live, in the same tab that holds your workspace. This article is about the wall between those two things — invariant SEC-INV-01 — and how the sandbox still feels alive to the code running behind it.

The rule

Preview frames use <iframe sandbox="allow-scripts"> and strictly never allow-same-origin. Without that flag the browser assigns the frame an opaque origin: generated code has no origin identity at all, so IndexedDB, OPFS, cookies, and the host page's storage are unreachable by construction — not by policy. Two more flags are banned as well: allow-top-navigation and allow-popups-to-escape-sandbox. The attribute is not written once and trusted: assertIsolatedSandboxAttribute re-validates it, throwing ERR_SANDBOX_MISSING_ALLOW_SCRIPTS or ERR_SANDBOX_ORIGIN_VIOLATION if a forbidden token appears.

What generated code actually receives

compileMultiFileSrcdoc turns the workspace's HTML entry plus its assets into one self-contained document, inlined into the frame via srcdoc — so the preview needs no network access to render:

  • Relative <script>, stylesheet, and <img> references are resolved against the entry file's directory, with ./, ../, and query-string forms normalized; if a path misses, a basename match across the workspace is the last resort.
  • Inlined workspace assets carry a data-veles-path marker; images become data URLs.
  • When the app uses the host bridge — or mentions localStorage/fetch — a bridge script is injected into <head>.

The bridge instead of storage

Inside the opaque origin, localStorage and sessionStorage throw. Generated apps instead get window.veles: kv.get/set/remove backed by per- workspace stores the host keeps, plus log() and opt-in device sensors (tilt, acceleration, pointer). The consequence is deliberate: sandbox state lives where the kernel can see and fence it, not where generated code can smuggle it.

The way back in is narrow

The frame may postMessage diagnostics out, but the host accepts a message only when all of these hold:

  1. The channel tag is veles:preview;
  2. its generation matches the currently mounted generation — a stale frame from a previous preview cannot whisper;
  3. its workspace sequence matches when one is expected;
  4. its type is exactly preview_ready, preview_error, or preview_log; and
  5. its message is a string, truncated to 2000 characters.

Everything else is dropped. Teardown is deterministic: the host removes the frame and its listener, and disposes cleanly (PreviewSandboxHost.dispose).

Script execution beyond the iframe

The workspace.run_script browser tool runs code in a protected worker where fetch and indexedDB do not exist, and dynamic imports of scanner-obfuscated module URLs are blocked before any request leaves the page. During development and preview serving, Vite supplies the protected worker and a stateless validation proxy; if the services are absent, tools fail with explicit errors rather than falling back to less-restricted execution.

Verify it yourself

npm test           # offline Node suites (sandbox host, srcdoc compilation)
npm run test:browser   # real Chromium: opaque-origin isolation, postMessage

tests/kernel-tools-preview.test.ts asserts the SEC-INV-01 attribute checks and srcdoc compilation; tests/browser/boundaries.spec.ts asserts run_script observes fetch: "undefined" and indexedDB: "undefined" and that the obfuscated-import request count stays zero; tests/browser/workbench.spec.ts asserts the mounted iframe's opaque-origin postMessage behavior.
